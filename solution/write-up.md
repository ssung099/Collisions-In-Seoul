# Collisions in Seoul

## Summary
This challenge provides a python script containing the encryption scheme used to generate the ciphertexts contained in `ciphertext.txt`. The encryption scheme contains a vulnerable "collision-resistant" hash function that allows you to break the encryption.

Artifacts:
- `chall.py`: the python script that contains the encryption scheme
- `ciphertext.txt`: the ciphertexts generated by `chall.py`

## Context
We are provided with a `.txt` file containing three hex-encoded lines. From `chall.py` lines 40–42:
```python
print((k1 + xor_delta).hex())
print((h1 + c1).hex())
print((h2 + c2).hex())
print(c3.hex())
```

The first line contains the key value `k1` used to encrypt the first plaintext and a value `xor_delta`, which is used to derive the second key. Line 2 and 3 contains the hash value of the (k, p) pair used to encrypt the provided ciphertext. Line 4 contains the ciphertext of the flag.

## Vulnerability
`chall.py` makes use of a vulnerable custom hash function `crhf`:

```python
def crhf(k, p):
    block_cipher = AES.new(k, AES.MODE_ECB).encrypt(p)
    return bytes(x ^ y for x, y in zip(block_cipher, k))
```

This computes:
 `crhf(k, p) = AES_ECB_k(p) XOR k`. 

Looking at the `h1` and `h2` values in `ciphertext.txt`, we can see that there is a collision in this hash function as `h1 == h2`. Using this collision, we can recover the secret value `p1` and use delta to calculate `k2` and `p2` as well.

## Exploit
Using the `k1` and `xor_delta` given to us along with the ciphertext, we can exploit the collision to recover the missing values to decrypt the ciphertexts.

Recovering `p1` is easy, since we are given `k1` and we can just isolate `p` in the function equation above.

```
h = AES_ECB_k(p) XOR k
h XOR k = AES_ECB_k(p)
p = AES_DEC_ECB_k(h XOR k)
```

With the recovered `p1` value and provided `k1` value, we can now decrypt the first ciphertext to get the following:
`NotFlag{국보29v=8wZNqBR8MOw}`

For the second `(k, p)` pair, we are not given the key value `k2` directly. Instead, the first line gives us `k1 || delta`.

From the source code, we can see that the second pair is generated with:

```python
delta = os.urandom(BLOCK_SIZE)
k2, p2 = generate_new_key(k1, p1, delta)
```

Given that there is a collision between the hash outputs of `(k1, p1)` and `(k2, p2)`, we can still recover both the `k2` and `p2` values.

Assuming that `k2` is some XOR offset of `k1` by `xor_delta`, we can generate a `p2` that collides with the original `(k1, p1)`.

```
k2 = k1 XOR xor_delta
y = AES_ECB_k1(p1) XOR xor_delta
p2 = AES_DEC_ECB_k2(y)
```

We can also verify this collision mathematically:
```
h1 = AES_ECB_k1(p1) XOR k1
h2 = AES_ECB_k2(p2) XOR k2
   = (AES_ECB_k1(p1) XOR delta) XOR (k1 XOR delta)
   = AES_ECB_k1(p1) XOR k1
```

Using the `(k2, p2)` pair recovered using `delta`, we can now decrypt the second ciphertext to get the following: 
`NotFlagAgain{2.0v=corrupted}`

### Remaining Solve Explanation
Searching up "국보29", we find a wiki page that refers to 29th Korean National Treasure, the Sacred Bell of Great King Seongdeok.

Taking the description into consideration, we can look for songs that could be related to this national treasure.

Searching for songs related to this national treasure, we can find a song called "No.29", a song released by BTS that contains the bell sound of this national treasure. Looking at the official YouTube video for this song, we can see that the URL contains `v=8wZNqBR8MOw` which is part of the first plaintext.

In a similar way, we can recover the corrupted text of the second plaintext. Searching for 2.0, we can see that it is another song by BTS in the same album "Arirang" as No.29. Looking at the YouTube URL for 2.0, we can find `v=YF4EN5YwjpA`.

Extracting the two ids from the two plaintexts, we can now decrypt the third ciphertext to get the flag.

## Remediation
The core issue is the use of a custom hash function:
`crhf(k, p) = AES_ECB_k(p) XOR k`

Because `k` is a known value, an attacker can directly recover the secret value `p` by calculating:
`AES_ECB_DEC_k(h XOR k)`.

A better hash function to use assuming that `k` is known is: `crhf(k, p) = AES_ECB_k(p) XOR p`.
This way, there is no simple rearrangement to isolate the value of `p`.

More generally, custom hash functions should not be used in real systems. Prefer existing, well-tested hash functions such as SHA-256 or SHA-3, and use constructions like HMAC or HKDF when keyed authentication or key derivation is needed.
